# 架构决策

## 已采用

1. Python 3.11 标准库 + SQLite。当前是单机 MVP、来源少、任务以 10 至 15 分钟为粒度，不需要 PostgreSQL 或可视化编排服务。
2. 外部 scheduler + 短进程 CLI。`collect` 适合由 cron 每 15 分钟调用；单源失败被隔离并记录，不需要常驻服务。
3. 统一增量采集管道。第一阶段实现公开 RSS、官方文档 sitemap（DeepSeek `/news/news*`），以及带官方 Bearer 的 X 只读时间线。X 对齐 AIHOT 的抓取方法：排除回复、丢掉纯转发、只保存推文 media，不订阅其摘要流，不爬 X 网页。配图只保留正文/og 与推文附图，丢掉 `profile_images`、作者头像和页眉图标。URL 去跟踪参数、外部 ID/URL/内容哈希去重，跨来源证据通过 `item_sources` 保留。热点确认靠独立来源数加公开讨论量；S4 可以单独成篇。工作台左栏主区是话题/新闻候选；订阅源「抓取成功 / 只刷这个」是源健康，不是新闻。`刷新全部` 先出库内列表，采集本身不再等翻译。左栏默认露出两条候选并在栏内滚动；配图收在独立栏内滚动。长文仍把页面加长，不把正文卡在面板里。
4. 透明热点规则。使用窗口数量、独立来源、7 天同期总体均值/标准差、可信来源门槛和冷却，不使用黑箱热点 Agent。
5. 事实先于草稿。事实结构、未知项和冲突完整落库；注册来源、可回溯、证据边界、引用长度和冲突处理是程序门禁。
6. 确定性 mock 生成器。没有 LLM 密钥仍能生成结构不同的微信和小红书草稿，并保留来源和 AIGC 声明。成稿前补本地相关旧闻和一次公开网页检索，只当素材，不把检索页当权威。
7. IT之家一类混合源只看标题是不是 AI 主题。正文里随口出现的 “AI 降噪 / AI 夜景” 或早报汇编不能进候选。
8. 发布仅为本地 dry-run 包。`publication_attempts` 保存幂等键、重试计数、状态、响应路径和错误；没有真实网络发布实现。
9. 成稿切口：独立「找切口」按钮、现场搜 `{短语} 争议`、人工多选。检索页只当素材。勾选后标题以主切口起笔，其余切口进开头。不建热搜库，不在点开新闻或点生成时搜索。

## 明确跳过

- n8n、PostgreSQL、Kafka、Kubernetes、Airflow、向量数据库、微服务和多 Agent 框架。
- X Filtered Stream、非官方网页爬取、长期 Cookie、模拟登录和绕过反爬。X 只读走官方 Bearer。
- 未核验的 S1/S2 员工 X 账号、图片生成与小红书自动提交。
- 把点赞或转发量当作唯一热点依据；它们只用于 S4 升温，不代替多源交叉。

## 升级条件

- 需要非技术人员维护复杂流程、多个长期工作节点或远程运行时，再评估 n8n + PostgreSQL。
- SQLite 出现持续写锁、数据量或并发实测瓶颈，再迁移数据库；不是预防性迁移。
- RSS 覆盖不足时，按官方 API -> sitemap/条件请求网页 -> 合规正文提取的顺序增加采集器。
- 只有业务证明必须秒级响应且 X 官方权限、预算、员工账号名单均已确认，才加入 Filtered Stream。
- 只有用户明确授权、凭证权限现场验证通过并增加端到端沙箱测试后，才设计微信真实适配器。小红书仍优先人工发布包或官方分享 SDK。
- 内容方向、目标受众和品牌语气明确后，再接入可审计 LLM 提供方；事实门禁和人工审批不得绕过。
