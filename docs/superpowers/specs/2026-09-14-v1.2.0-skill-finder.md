# AutoPosting 1.2.0 — Skill 查找器

Patch 1.2.0 skill-finder half. Binding for the skill-finder implementer.

## Goal

Skill 查找器页：图片模块可见；查找过程边运行边吐结果（先 skill，全部 skill 展示完再吐图片）；相近二次查找不能空手；缺口阶段/缺口 skill 完全不出现。

## Current code (1.1.3)

- `src/autoposting/skill_finder.py` — `find_skills` blocks until decompose + search + `write_article`. Returns `images: []`. Gaps set `stage["gap"]=True` and stay in `stages`.
- `src/autoposting/web.py` — `POST /api/skills/search` waits for the full payload; `POST /api/skills/render` is a second click (`#skills-render-btn`). Gallery is `#skills-gallery` inside `#skills-studio`. CSS: `#skills-studio{display:none}` until `body.lane-skills`.
- Quality: `passes_quality` requires SKILL.md (or path markers) plus stars/registry/freshness. `_FetchBudget` 40 calls / 45s. GitHub errors and budget `RuntimeError` are swallowed by `_try_get` / `_searcher` as empty.
- Cover 大字报: `docs/image_prompts/skill_cover.md` + `skill_cover.py`. Weekly-style cards: `render_skill_package` → `render_weekly_visual`.

## Requirements

### 1. Image module must be visible on the skills lane

Root cause to confirm (do not guess past this): `#skills-studio` / `#skills-gallery` may be collapsed, empty, or below the fold because images stay `[]` until a separate 「生成图片」click, and the GitHub weekly 生成图片 controls live in the left header while skills' controls live only in the right studio.

Must:

- On `body.lane-skills`, the right pane shows a first-class image module with the same visual weight as GitHub weekly (`#github-studio` / `.gh-gallery`): toolbar + gallery grid.
- Empty state is visible (placeholder copy or queued tiles), not a blank panel.
- After skills exist, auto-start render. Keep 「生成图片」 as a retry, not the only way to see the module.
- Cover is the theme 大字报 (existing `skill_cover` path). Other cards stay weekly HTML visual, cover 3:4.

### 2. Stream results: skills first, images only after every skill is shown

`find_skills` / `/api/skills/search` must not wait for images (or for the full article+images package) before the UI can show skills.

Required event order:

1. Coverage stages that still have at least one real skill (no gap stages).
2. Each accepted skill, incrementally, left sidebar `#skill-list` (and chips) updates as they arrive.
3. When the skill list is complete, then start image generation and stream/show images in `#skills-gallery`.
4. Article text may arrive with or after the completed skill list, but **never before the first skills**, and **must not delay showing skills**. Images must not appear until all skills that will be shown are already on screen.

Implementation constraints:

- Python 3.11 stdlib HTTP server. Prefer: in-memory job + `GET /api/skills` polling (existing snapshot) with `phase` in the payload (`searching` | `skills_ready` | `rendering` | `done` | `error`). Do not add third-party deps.
- Persist via existing `save_skill_finder` JSON. Do not invent a second source of truth.
- `on_event` / callback inside `find_skills` so tests can assert order without HTTP.
- Abort/cancel via existing wait-banner AbortController still stops the job.

### 3. Second similar search must not return zero skills

User symptom: two similar queries, overlapping decompose branches/stages, second run finds **no** qualifying skill.

Investigate with a failing test that replays: first `find_skills` succeeds; second call with overlapping stages where GitHub GET/search returns 403/empty/timeout. Today that yields `skills=[]`.

Fix the root cause, not the screenshot:

- Process-local cache for GitHub GET and search URLs (TTL ~15 minutes). Cache hits do not consume fetch budget.
- Reuse previously accepted skills from the last snapshot when the new coverage map still contains their stage (match by `source_id`).
- HTTP 403/429/timeout is not “this repo is not a skill”. Do not drop a hit solely because `fetch_skill_md` failed on rate-limit.
- Budget exhaustion returns whatever was already collected; it must not clear `collected`.
- Each search still gets a fresh `_FetchBudget`. Cache + reuse make overlapping queries stable.

### 4. Gap skills/stages do not exist in any output

Treat `gap: true` stages and any placeholder “缺口 skill” as absent:

- Not in left chips (`#skill-stage-chips`) or `#skill-list`.
- Not in images / gallery jobs.
- Not in `write_article` input. Update `docs/skill_finder/PACKAGE_ARTICLE.md`: delete the 「缺口」section. The model must not mention missing stages.
- `coverage["stages"]` passed to article and UI is only stages that have ≥1 accepted skill.
- Do not render `is-gap` chips.
